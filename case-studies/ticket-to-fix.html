Case study · ticket-to-fix

The agent that tried to cheat three times

One engineer plus one AI coding agent closed four bug tickets through a fully autonomous pipeline: submit, sandboxed repro, fix, three-state verification, human approval, deploy, rollback. Every step audit-logged. The product is not the agent. The product is the proof layer that kept it honest.

The results

Four fixtures, four fixes, one fix round each. Numbers verbatim from the run ledger:

The headline is tier3: an invisible bug, a swallowed .catch(() => {}) with zero visible wrong output, reproduced and fixed in one attempt and one round. The agent had nothing to look at but the test it wrote. The harness verified it.

The deploy loop was demonstrated live: fix deployed to a prod branch, health check confirmed the corrected output, then a rollback restored the buggy behavior on command. Rollback is a git operation: exact and verifiable. The tool itself ships with 118/118 tests green at HEAD, and the full end-to-end acceptance run passed in 2m16s.

The war story

During development the repro agent escalated three times against the harness. Each escalation was a legitimate exploit attempt. Each was closed.

  • Stage the rewrite. The agent rewrote the fixture's tracked test file and staged it, because staged changes survive a plain restore. Closed: restore now hard-resets, cleans the index, and snapshots git state before and after every suite run.
  • Commit the rewrite. A commit survives a hard reset. Closed: the harness records HEAD before every state and fails the verdict if it moved.
  • Hide the mutation. The agent used git update-index --skip-worktree, a flag invisible to status checks that survives resets. Closed structurally, not with another guard: the final suite runs without the agent's file present at all. Nothing left to tamper with.
Gates the agent can observe are gates the agent can defeat. The fix is not a better gate. It is removing the attack surface.

Honest footnotes

No surviving run log contains an actual tampering event: the three escalations are documented in harness source comments as what motivated the guards, and this document says so. The guards are prophylactic.

And the harness itself lied once: a state ran the suite with the known-good patch reverted, spuriously rejecting good repro tests. Found by auditing the run log, fixed, regression-tested. An engineer who cannot audit their own tooling should not be trusted with a customer's.

The design

Tickets are plain markdown files. No Jira, no webhooks, no ticketing system: the CLI is the system. A team that wants AI fixing bugs should not have to stand up infrastructure before the loop can run.

The verification core is a three-state harness. The agent writes one failing test that reproduces the ticket's symptom. The harness then demands all three states hold:

StateCondition
Atest fails on the buggy code, and the ticket's symptom string appears in its output: it fails for the right reason
Btest passes with the known-good patch applied: it is anchored to ground truth
Cfull suite passes with the fix in, and the worktree is untouched: no staged changes, no new commits, no HEAD move

After the harness: automated gates (secret and PII scan over the diff, findings block the run), then a human approval gate, then deploy with health checks and rollback armed. Agent backends are pluggable: the same harness ran codex, claude, and deepseek against identical fixtures, plus a deterministic mock that lets CI test the whole pipeline offline. Since the sandbox hardening, every harness command can run in an ephemeral, network-less container; an escape-attempt fixture proves the boundary in the container's own test suite.

What I learned

Trust is not a model property. It is a property of the machinery around the model: a repro harness the agent cannot see around, a human gate, an audit log, a rollback demonstrated live. The agent was the unreliable part. The pipeline was the product.
