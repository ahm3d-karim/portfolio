A society's shortlisting, rebuilt

The LUMS Religious Society's member shortlisting ran on spreadsheets and WhatsApp: manual updates, unverifiable entry codes, no shared source of truth. I rebuilt it as a live portal with role-based access, server-verified entry codes, and a stats dashboard. It runs in production for the society's team today.

This is the least flashy project on this site and the most telling one: it has real users, real data that must not leak, and real consequences when a number is wrong. There is no public link here on purpose. The code is private because it holds a student society's member data; the deployment is login-protected. An architecture walkthrough is available in an interview.

The constraint that shaped it

The society already had a legacy backend that could not validate entry codes in real time: checking a code meant a page refresh against stale data. The fix was a migration to a realtime backend, shipped with a compatibility path kept open so a rollback to the old system stayed possible until the new one proved itself. Migration discipline mattered more than framework choice: numbered, ordered migrations; a rollback plan; secrets kept out of the client entirely.

Day to day, the portal ingests updates from the society's membership sheet through a forwarder with catch-up logic, verifies codes through a server-side check that the client cannot bypass, and computes the transfer and gender/batch statistics the EC actually argues about.

Production is where the easy problems stop being easy: staleness, trust, and rollback all stop being theoretical.

The collaboration

This is a joint build with the society's team. My changes ship as reviewed pull requests against the upstream repo, each with its own verification pass: typecheck, build, and lint clean before merge. Working on someone else's production system is a different discipline from shipping your own side project: you optimize for boring, reversible changes, and you leave the codebase legible for the next person.

What I learned

The hardest problems in this build were organizational, not technical: who is allowed to see what, what happens when a code leaks, how to retire an old system without a big-bang cutover. Those questions do not appear in tutorials, and they are exactly what a forward-deployed engineer lives in.
